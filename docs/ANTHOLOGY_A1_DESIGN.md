# A1 Architecture Decision Record: XGBA-native Grand Anthology

**Status:** DESIGN ONLY. User requested a proper adversarial plan; no A1 gameplay, linker, emulator or save code has been implemented. Implementation requires a separate explicit start instruction. Date: 2026-10-31.

## 1. Definition of done

A1 delivers an independently built, natively **XGBA-only** version of the existing Kanto/Johto/Hoenn Grand Anthology. It must (a) boot and play in the frozen XGBA E7 emulator, (b) render **actual map data moved outside the legacy 32 MiB cartridge window**, (c) retain all current story/maps/battles/region transitions and native v13 128 KiB Flash save layout, (d) verify high-address asset bytes through XGBA CPU access and a genuine map load, (e) build deterministically with a capacity/recovery/error-aware packer and branch-only CI, and (f) have one concise user acceptance pass after automated checks.

**Large-batch scope:** Move all **1,043 existing MapLayout objects' map.bin/border.bin source blobs** (up to 2,086 nonempty payloads) into the separate XGBA ROM window; do not stop after moving one proof-of-concept map. Metadata, scripts and executable code remain native. Also place the **actual RegionHub layout** near the 255 MiB end of the extended window, rather than testing only an artificial sentinel. Do not duplicate 20 Hoenn worlds.

**A1 deliberately excludes:** new regions, PC or bag changes, 16 MiB extended save, old-save import/migration, version bumps to the game save, battle-engine rewrites, XGBA smartphone port, new website/deployment, production merge. A1 builds a scalable asset pipeline useful for future region artwork, but relocating audio/tileset gfx/sprites can wait until their specific pipelines are separately audited.

## 2. Verified source invariants and addressing

- Working branch: `DevElectrum/grand-anthology:xgba/expansion-lab`. Source freeze: `xgba/pre-expansion-20261031` at `ee129df07e5d8b4ce8d6ebe134fa4399eb921997`. `main` is the unchanged three-region source anchor (apart from docs), while `DevElectrum/pokemon-mosaic` independently develops the ordinary-emulator-compatible game.
- `ld_script_modern.ld` has `ROM ORIGIN=0x08000000 LENGTH=32M`; **keep it that way in A1**, keeping `.text`, scripts, metadata and other `.rodata` in native mapped ROM with normal GNU ARM relocation and linker safety. Do **not** simply enlarge this region or link directly into XGBA's 0x10 window and run `objcopy -O binary` across a huge discontinuous ELF image.
- XGBA E7, frozen at `DevElectrum/xgba:xgba/e7-accepted-20261031`, maps a tagged cartridge's file bytes at **CPU 0x10000000 + file_offset**, with file offset 0..0x0FFFFFFF. Native 0x08000000..0x09FFFFFF sees the first 32 MiB of the same file. Valid extended addresses are **0x12000000..0x1FFFFFFF** for offsets beyond native 32 MiB; the first 32 MiB of the extended view aliases the resident prefix. Plan and test reads at 0x14000000, 0x18000000, 0x1C000000 and 0x1FF00000/0x1FFFFFFF.
- Real game generated by `tools/mapjson/mapjson.cpp:generate_layout_headers_text`: emits `<Layout>_Border`, `<Layout>_Blockdata` as `.incbin` followed by `<Layout>` metadata of exactly `width,height,border ptr,map ptr,tilesets,format flags`. `data/layouts/layouts.json` has **1,043 layouts**, partitioned by source format 439 Emerald, 259 Johto, 345 FRLG, with 2,086 paths. `data/maps/map_groups.json` contains **101 groups and 1,194 maps**. `gMapLayouts[layoutId-1]` is looked up in `src/overworld.c:GetMapLayout`.
- `src/fieldmap.c:InitBackupMapLayoutData` and `FillConnection` read `MapLayout.map` directly, including connected neighbors. **Therefore changing only `GetMapLayout` at runtime is insufficient**. Keep metadata resident and give all generated layout metadata their correct immutable XGBA high-address `map`/`border` pointers at assembly/link time. That automatically covers ordinary map initialization, saved-header reload, connections and other direct layout references.
- Current game still saves v13, refuses pre-v7 layouts, uses 128 KiB Flash, `BPEE` code and 3-region flags. A1 does not change any. The E6/E5 extension save requires matching `0xBC` revisions and on-disk superblocks; do not activate it in A1.

## 3. Chosen architecture: extended asset manifest + generated absolute symbols

**Preferred** over direct huge-ROM linking, post-build blind pointer patching, runtime map copying/caches, or replacing the complete Emerald test harness.

### A. Deterministic asset source-of-truth

Create `tools/xgba_a1_assets.py` with a stable, versioned JSON manifest derived from `data/layouts/layouts.json`, retaining exact existing layout IDs and `width/height/format/tilesets`. A layout's original `map.bin` must be exactly `2 * width * height` bytes; borders retain their declared source lengths and required format-specific checks. Reject missing/empty (unless baseline legitimately allows empty), unaligned, overlapping, duplicate-symbol, out-of-bounds, changed-size and inconsistent-ID entries. Never enumerate files in nondeterministic OS order. Emit both (i) absolute-symbol mapping for generated assembly and (ii) exact file data/offset/digest packing plan in one invocation. Require stable ordering and explicit bounds/reserved capacity for future content.

### B. Region-oriented physical file offsets, independent of gameplay region IDs

Use separate capacity lanes in the **256 MiB file**, with CPU address = 0x10000000 + file offset:

| File offset lane | Intended A1 content | CPU address start |
| --- | --- | --- |
| 0x00000000–0x01FFFFFF | Original ELF executable/native tables, first 32 MiB unchanged except cartridge identifier and final header checksum | 0x08000000 native |
| 0x04000000–0x07FFFFFF | Emerald-format layout payloads (439 layouts) | 0x14000000 |
| 0x08000000–0x0BFFFFFF | FRLG-format layout payloads (345 layouts) | 0x18000000 |
| 0x0C000000–0x0EFFFFFF | Johto-format layout payloads (259 layouts) | 0x1C000000 |
| 0x0FF00000–0x0FFFFFFF | **RegionHub actual map and border**, unique A1 read signatures, verified end-of-ROM marker | 0x1FF00000 |

**Important:** `layout_version` is the **tileset/metatile source format**, not a reliable player-region identifier; Johto may use FRLG-layout assets. The lanes here are *file organization only*, not world-specific gameplay ownership. An explicitly selected RegionHub layout overrides its FRLG lane. No changes to `MapLayout.isFrlg` or `isJohto`, which control correct width/attribute interpretation. Reject lane overflow or any size/overlap conflict, never silently spill into another lane. All currently selected layout source blobs must be placed exactly once with original bytes.

### C. Build-time pointer correctness

Modify mapjson's layout generation path (or its generated assembly stage with a strictly tracked dependency) for **XGBA-A1 only**: replace each moved `*_Border`/`*_Blockdata` `.incbin` with exported **absolute symbol definitions** (e.g., `.global NAME; .set NAME, 0x1xxxxxxx`). Keep each `MapLayout` metadata definition and `gMapLayouts` order unchanged. Link must resolve every reference to these symbols without copying the moved blobs into 32 MiB. The same manifest generates both the pointers and the packed bytes. Add an all-layout verification that every compiled pointer equals its manifest-resolved file offset plus 0x10000000. Never manually patch arbitrary values in the compiled image; inspect linked layout pointers by ELF/symbol map.

Build outputs and generated objects must use **a dedicated A1 build directory or cleanly isolated variant** so switching baseline vs A1 cannot reuse stale native objects with incorrect absolute pointers. Make dependencies must regenerate correctly after an asset or layout JSON change.

### D. Tag and package in correct order

1. Build resident optimized game (same ARM7TDMI modern toolchain, same native 32 MiB linker bound) in A1-only directory, ensure normal ELF symbols, baseline gameplay and no high-ROM code execution are required.
2. Convert ELF to raw native ROM and run existing gbafix once.
3. Stage a **new exact 256 MiB** sparse ROM in a dedicated disposable output path. Write native prefix, then byte-accurate manifest payloads to assigned extended file offsets. Require the source and output paths differ and fail on any unexpected existing output.
4. Write `XGBA256` in header reserved bytes `0xB5..0xBB`. **Keep software revision `0xBC=0x00` for A1** (do not set E5/E6; this selects XGBA extended *ROM* while deliberately retaining native Flash1M). Recalculate/validate official GBA header complement `0xBD` after any header edits; preserve maker, `BPEE`, game title and other cartridge fields.
5. Insert known integrity markers, including the last byte `file 0x0FFFFFFF = guest 0x1FFFFFFF`. Verify **every** asset byte and manifest digest from the completed ROM, all capacity/boundary checks, native prefix (allowing only declared header edits), tagged boot capability and correct revision.
6. Only on successful verification atomically publish `xgba-anthology-a1.gba`. Never overwrite a user save or the original `pokemonworld-release.gba`. Never upload binary ROMs or save images to GitHub or Actions artifacts.

## 4. Performance/error handling planned before coding

**Hotpath budget:** No decompression/copy of whole regions into EWRAM, no per-map scan over a 256 MiB ROM, no runtime asset lookup through Python-like manifests. `MapLayout` pointers remain normal constant 32-bit memory pointers and map loading does the same size copies as before. Target median map-entry and hub-to-region transition times **within 20% of the unmodified game** on the same XGBA binary and 1x speed. Record baseline 5 repetitions, then 5 A1 repetitions. Cold ROM open is separately reported because the emulator's existing whole-ROM CRC touches 256 MiB once; provisional acceptable additional cold-launch cost **up to 3 seconds on Nyx**, beyond which inspect once and fix if avoidable before acceptance. These are engineering targets, not claims of tested timing.

**RAM budget:** Resident map metadata remains in ROM and raw layouts are accessed in-place; aim for **no persistent additional EWRAM buffers** beyond a tiny compatibility/status flag. Keep the original GBA 256 KiB EWRAM and 32 KiB IWRAM limits. No allocation proportional to ROM size, region count or full map count at runtime.

**Critical interface audits:** verify 8/16/32-bit loads, alignment, exact address boundary, the existing `CpuCopy16`/BIOS CpuSet path, the actual `FillConnection` neighbor read, border walking, tilesets, palette and collision data, scripted dynamic layout substitutions, save/reload layout restoration, Fly/teleport/escape and hard emulator restart. **DMA nuance caught during planning:** XGBA's accepted `src/gba/dma.c:GBADMAWriteSAD` explicitly allows high-ROM source addresses for DMA channels 1–3 when a tagged ROM is mounted, but DMA0 retains the original restricted source mask; DMA timing/special paths have not been demonstrated against actual Anthology graphics. A1 relocates raw map geometry read by the CPU/BIOS-copy path, NOT tile graphics that might need DMA/VRAM streaming. Add a targeted DMA1/3 high-ROM-to-RAM regression for future asset classes; do not equate successful CPU reads with safe DMA transfers. Verify that no code path truncates pointers to 24 bits or silently masks region 0x10 to 0x08. These checks are driven by deterministic CI fixtures, not repeated user testing.

**Safe missing-ROM behavior:** A1 boot should check a few very cheap high-address canaries through CPU reads **before any relocated map loads**. If XGBA ROM addressing is unavailable, a manifest revision is incompatible, or an integrity marker is absent, show a clear fatal/unsupported-runtime message and **block gameplay/save writes** if the emulator reaches the game. A stock emulator may reject the tagged >32 MiB file earlier; do not promise a UI in that case. Do not compute a 256 MiB CRC every boot/map entry in game; the packer verifies all assets and the canary is a small runtime guard.

**Build/error recovery:** collisions, invalid map dimensions/format, missing files, stale generated objects, native overflow, incorrect game header checksum, wrong save-extension revision, readback mismatch and truncation fail CI with an exact affected layout/path. Keep the original source branch and pre-expansion checkpoint intact; failed A1 builds never replace last-known-good ROM. Corrupted or missing 128 KiB saves must follow inherited version/refusal behavior; all A1 user tests use **a backup/copy** of old saves, no automatic conversion.

**Future capacity trap:** `data/maps/map_groups.json` already uses 101 map groups; overworld warps/current maps pass map group/map number through signed 8-bit slots in several places. A1 must flag this in the A3 architectural ledger. Do not add nine regions by simply appending enough map groups to overflow those saved-ID fields. A1 itself must **not change any existing map IDs**, so native v13 saves stay compatible.

## 5. One integrated A1 implementation, three quality gates

### Gate 1: preflight before any code generation

Capture native baseline at the frozen source revision (ROM size, symbol map, EWRAM/IWRAM, save v13, header/game code). Enumerate every one of 1,043 map layouts and its files, width/height/format and duplicate symbol/ID checks. Check any map-format exceptions. Verify actual XGBA savedata behavior with `XGBA256` tag and header revision zero. Confirm all required high-ROM read and BIOS copy paths via existing emulator test infrastructure. Record exact baseline results before altering generator/packer.

### Gate 2: commit one coherent source implementation and close automated CI

Deliver manifest/generator, generated absolute-symbol path, packer/staged `make xgba-a1` target, boot guard, version/bytes checks, and branch-specific GitHub CI **as one major feature**. Automated tests should include: all original layout file sizes and checksums; generated symbol pointers match packed offsets; native ROM remains below 32 MiB; every asset readback; high-boundary and final-byte checks; title/header/checksum validity; emulator direct CPU reads **and BIOS map copies** from high ROM; map connections and border reads; game three-region save/load regression; a deliberately malformed/short/truncated cartridge; unchanged v13 native saves. Avoid CI ROM uploads and automatic website deployments.

If the native ROM does not materially reclaim space, inspect linked-symbol disassembly/map and fix the generator, rather than claiming success because a 256 MiB file exists. Measure baseline and final ROM occupied bytes and clearly report real linked-byte savings.

### Gate 3: ONE user's gameplay acceptance wave

After CI green, build A1 in its separate local worktree and test with a **disposable copied 128 KiB v13 save**, never a live Mosaic/Anthology save. On XGBA Qt for Nyx Linux: boot, enter the RegionHub (actual payload near 255 MiB), traverse representative Kanto/Johto/Hoenn maps (all layouts relocated), walk across a live map connection, enter a battle, save, quit the emulator and hard-restart from the copied save. Confirm party/items/region intact and capture rough cold boot and map/region travel speed. Use scripted CI warp fixtures to minimize manual movement. No need to repeat the user's Kanto and Johto campaigns.

**A1 accepted** only with separately confirmed source/build CI and one in-game test. Then freeze `xgba/a1-accepted-<date>` and update handoffs. If either fails, fix the isolated cause and rerun only the affected automated tests plus the single impacted human check; do not restart three waves of unrelated QA.

## 6. Post-A1, deliberately separate

A2 will design the actual native-compatible Flash-to-XGBA 16 MiB save migration, PC data model, bag schema, dual-copy CRC/recovery, performant lookup and collection UI. A3 will redesign regional progress/map IDs, independent of asset offsets. A4 covers modern battle rules. A5 begins actual new Sinnoh gameplay. No A1 task is allowed to silently pull these into scope.
